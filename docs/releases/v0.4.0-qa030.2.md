# AgentRoom v0.4.0-qa030.2

This QA candidate is the exact follow-up build for the one-install,
one-Device physical acceptance flow. It keeps the public-CA-default and
pairing-scoped private trust contract from `v0.4.0-qa030.1`, fixes terminal
Delivery backlog accounting, and records the currently connected Bridge build
separately from the immutable version used during initial pairing.

## Highlights

- Excludes unaccepted Deliveries for terminal Runs from actionable queue depth,
  pending-count, and oldest-age metrics while preserving the immutable Delivery
  row as trace evidence and preventing reconnect dispatch.
- Adds migration 0048 and authenticated Presence observation so the same paired
  Device can upgrade in place and report its current packaged Bridge version
  without rewriting its initial pairing version or Device identity.
- Emits canonical, no-leading-`v` Bridge build versions while Central accepts
  the legacy leading-`v` hello during the rolling upgrade window.
- Suppresses empty Windows console windows when managed Codex and other Runtime
  processes start from the Desktop application.
- Keeps reasoning-summary consent discoverable and editable after Bridge setup,
  without requiring the Bridge connection to be stopped first.
- Tightens the database-bound schema-v3 physical evidence verifier so initial
  pairing identity, current package identity, connection epoch, TLS profile,
  credential ownership, and heartbeat ownership are reviewed as distinct facts.

## Upgrade and Compatibility Notes

- Upgrade Central first, then install the new Bridge package over the existing
  Windows installation. Central accepts the legacy `v0.4.0-qa030.1` hello while
  the new Bridge emits `0.4.0-qa030.2`, so the same Device can reconnect across
  the rolling upgrade.
- Do not revoke, delete, or re-pair the existing Device. The in-place Bridge
  installer preserves owner state and the Device credential; migration 0048
  stores only the independently observed current Bridge build identity.
- Back up the Central SQLite database and Bridge owner state before upgrading.
  Rollback must use version-aligned binaries and the matching database backup.
- Publicly trusted HTTPS remains the default. A scoped-private deployment pins
  its pairing-delivered CA only to the exact Central origin in Bridge owner
  state. The flow must not install a root in the Windows trust store, disable
  TLS verification, copy a Server Token, or copy a Device credential.

## Artifacts

The protected Release workflow publishes five portable Bridge CLI archives,
two native macOS Desktop ZIPs, one Windows Desktop portable ZIP, one Windows
current-user installer, four checksum-pinned Central archives, four separate
Central checksum pins, one outer `SHA256SUMS`, and four license files. The
tagged verifier requires exactly 22 assets and checks their names, checksums,
archive closure, launchers, architectures, embedded versions, GUI and installer
metadata, Central source/schema metadata, and license contents before and after
Draft upload.

## Remaining Gates

- `QA-002`, `QA-028`, and `QA-030` remain blocked until the same physical
  Windows Device is upgraded in place to this exact candidate, reconnects with
  fully drained packaged metrics, and produces one reviewed schema-v3 record.
- That final record must include the safe Codex version and human-confirmed
  no-OS-CA, no-TLS-bypass, no-Server-Token-copy, and no-Device-credential-copy
  facts. The prior partial record is not promoted automatically.
- `BRG-013` still requires a real macOS logout/login or restart proving exactly
  one Desktop instance and no credential stored in the LaunchAgent.
- Packages remain unsigned, unnotarized, and manual-update-only.
- `v0.2.0` remains the stable Latest release while this QA build is evaluated as
  a prerelease.
