# AgentRoom v0.4.0-qa030.3

This QA candidate is the lifecycle-safe follow-up build for the one-install,
one-Device physical acceptance flow. It keeps the public-CA-default,
pairing-scoped private trust, terminal Delivery metric fencing and independent
current-Bridge build observation from `v0.4.0-qa030.2`, while adding the
Central authority preflight required before another physical upgrade attempt.

## Highlights

- Validates the existing Owner recovery credential's file boundary and exact
  controller-generated format in `agentroomctl doctor`, instead of accepting an
  empty but mode-`0600` file.
- Stops `agentroomctl upgrade` with `UPGRADE_SECRET_INVALID` before backup,
  target Compose validation, image build, container replacement or manifest
  mutation when the Owner recovery credential or optional legacy Server Token
  is missing, malformed or unsafe.
- Never regenerates or replaces authority for an existing Owner; recovery
  requires the exact original credential under the documented permission
  boundary.
- Retains migration 0048 and authenticated Presence observation so one paired
  Device can report the currently running packaged Bridge build separately
  from its immutable initial-pairing version.
- Retains terminal-Run Delivery metric fencing, suppressed Windows Runtime
  console windows, and post-setup editing of reasoning-summary consent.

## Upgrade and Compatibility Notes

- Back up the Central SQLite database and Bridge owner state before upgrading.
  Run the packaged `agentroomctl doctor` against the existing data root. If it
  reports `SECRET_INVALID`, restore the exact original Owner recovery file;
  never generate a new value for an existing Owner.
- Upgrade Central first, then install the new Bridge package over the existing
  Windows installation. Do not revoke, delete or re-pair the Device. The
  current-user installer preserves Bridge owner state and its Device
  credential.
- Central accepts the legacy `v0.4.0-qa030.1` Bridge hello during the rolling
  upgrade, while this Bridge emits the canonical `0.4.0-qa030.3` build value.
  Migration 0048 records only the independently authenticated current build.
- Publicly trusted HTTPS remains the default. A scoped-private deployment pins
  its pairing-delivered CA only to the exact Central origin in Bridge owner
  state. The flow must not install a root in the Windows trust store, disable
  TLS verification, copy a Server Token or copy a Device credential.
- Rollback must use version-aligned binaries and the matching database backup;
  forward database migration is not evidence that an older image is safe.

## Artifacts

The protected Release workflow publishes five portable Bridge CLI archives,
two native macOS Desktop ZIPs, one Windows Desktop portable ZIP, one Windows
current-user installer, four checksum-pinned Central archives, four separate
Central checksum pins, one outer `SHA256SUMS`, and four license files. The
tagged verifier requires exactly 22 assets and checks their names, checksums,
archive closure, launchers, architectures, embedded versions, Desktop and
installer metadata, Central source/schema metadata, separate internal checksum
pins, and license contents before and after Draft upload.
