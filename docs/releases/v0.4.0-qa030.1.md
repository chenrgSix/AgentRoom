# AgentRoom v0.4.0-qa030.1

This QA candidate packages the unified Central installation and Device
onboarding flow, the Task/Run/Result work model, and the revised deployment TLS
contract: public CA by default, pairing-scoped private trust when explicitly
selected, and manual CA handling only as an advanced diagnostic mode.

## Highlights

- Adds a reentrant `agentroomctl` lifecycle for installing, inspecting,
  upgrading, backing up, restoring, and uninstalling one version-aligned
  Central deployment.
- Adds one-time, short-lived Device pairing links that launch the installed
  Bridge, preserve local owner authority, and avoid copying Server Tokens or
  Workspace paths through the browser.
- Adds versioned Tasks, immutable Run-attempt manifests, Agent-proposed Results,
  review, correction, recovery, Artifact evidence, and Result-gated completion
  across Server, Web, contracts, and Bridge commands.
- Makes publicly trusted HTTPS the default deployment profile. A private
  deployment carries its CA only inside the exact pairing flow, pins it to the
  paired Central origin in Bridge owner state, and never requires installing a
  root in the Bridge host operating system.
- Adds two-authority private-CA rotation with acknowledgement from every
  eligible paired Device before promotion and with an explicit rollback path.

## Upgrade and Compatibility Notes

- Upgrade Central Server, Web, controller, and Bridge together. Database
  migrations 0041 through 0047 add pairing sessions, Workspace aliases, the
  Task/Run/Result model, pairing trust, and private-CA rotation acknowledgements.
- Existing `v0.3.0-rc.6` Bridges remain useful for their supported flows, but
  they do not implement the new pairing-trust contract. Do not mix an older
  Bridge with a strict scoped-private deployment.
- For the normal path, configure a DNS name and a publicly trusted certificate;
  the pairing link intentionally contains no CA material. Use
  `private_scoped_ca` only for a private deployment that cannot obtain public
  trust. `manual_ca` remains an explicit advanced compatibility mode and is not
  the onboarding default.
- Private trust is stored only in Bridge owner state and only for the paired
  Central origin. The flow must not write to the Windows or macOS system trust
  store, disable TLS verification, or fall back from public trust to a private
  root silently.
- Back up the Central SQLite database and Bridge owner state before upgrading.
  Rollback must use version-aligned binaries and the matching database backup.

## Artifacts

The protected Release workflow publishes five portable Bridge CLI archives,
two native macOS Desktop ZIPs, one Windows Desktop portable ZIP, one Windows
current-user installer, four checksum-pinned Central archives, four separate
Central checksum pins, one outer `SHA256SUMS`, and four license files. The
tagged verifier requires exactly 22 assets and checks their names, checksums,
archive closure, launchers, architectures, embedded versions, GUI and installer
metadata, Central source/schema metadata, and license contents before and after
Draft upload.

## Remaining Gates

- `QA-030` remains active until two physical hosts complete a clean public-CA
  or pairing-scoped-private rehearsal without changing the Bridge host OS trust
  store.
- `QA-002` and `QA-028` remain blocked until the same installed Device completes
  reviewed online and offline/reconnect Runs with a credentialed local Codex.
- `BRG-013` still requires a real macOS logout/login or restart proving exactly
  one Desktop instance and no credential stored in the LaunchAgent.
- Packages remain unsigned, unnotarized, and manual-update-only.
- `v0.2.0` remains the stable Latest release while this QA build is evaluated as
  a prerelease.
