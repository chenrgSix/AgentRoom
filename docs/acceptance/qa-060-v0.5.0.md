# QA-060 ConveneWire v0.5.0 Stable Release Admission

Status: goal and admission gates frozen by the Owner on 2026-09-04 before
stable tag creation, Draft creation, packaging or publication. Delivery state
lives only in `docs/TASKS.md`.

## Goal

Publish one new immutable `v0.5.0` stable Latest release containing the
completed Governed Software-Team Execution Core and the accepted `QA-059`
stability repair. Stable admission is evidence-based and has no implicit
elapsed-time requirement. Freezing this record fixes the rules; it does not
claim that the rules have passed or authorize publication.

The published `v0.5.0-rc.3` prerelease remains immutable evaluation evidence.
Its tag and 22 assets must not be moved, replaced, deleted or relabeled.
Unpublished `v0.5.0-rc.1` and `v0.5.0-rc.2` remain immutable zero-asset
failed-closed records. Stable Latest remains `v0.4.2` until every gate in this
record passes.

## Stable Product Boundary

The stable claim is limited to source-available, self-hosted use by trusted
small Teams:

- humans govern exact Plans, approvals, evidence adoption and repository
  integration operations;
- Central governs Plan, scheduling, bounded authorization,
  Evidence/Proof/Adoption and operation-receipt facts;
- repository paths, Git remotes, Git/SSH credentials, fetch/pull/push,
  worktrees and Git command execution remain Client/Bridge and machine-Owner
  authority;
- the Remote Evidence implementation remains an optional,
  credential-free-by-default extension and is not a Core or stable-admission
  dependency; and
- packages remain unsigned and unnotarized, updates remain manual, and the
  release is not a public multi-tenant or general-production admission.

`BRG-013`, `WEB-050` and `QA-038` remain separate active work. Stable
publication does not close them and does not claim macOS login-restart,
exhaustive Hosted-Agent production-browser states, a paid/live provider,
multiple physical execution machines, signed distribution, automatic updates
or a production deployment. A future claim in any of those areas requires its
own accepted task and current evidence.

## Pre-Tag Admission Gates

Before creating a stable tag or Draft, all of the following must be retained:

1. Review the public RC, repository issues and known release findings. No
   unresolved P0 or P1 correctness, security, recovery, upgrade, data-loss or
   packaging finding may remain in the admitted scope.
2. Select one full commit on `main` after the frozen admission record. The
   worktree must be clean, local `main` must equal `origin/main`, and every
   runtime or packaging change after `v0.5.0-rc.3` must have a named task,
   regression evidence and an updated boundary in this record.
3. That exact commit must pass the complete main CI: Repository, Go, native
   macOS Desktop and native Windows Desktop jobs. A retry is evidence only when
   the original failure is diagnosed and any repair is committed separately.
4. A disposable installation must take and verify an online `v0.4.2` Central
   backup, upgrade the exact candidate through migration `0086`, preserve the
   installation, Device and Agent identities, and report the candidate release
   version and source commit from the running service.
5. Exact candidate packages must complete one Owner-reviewed product smoke on
   supported hardware: Discussion decision, Plan proposal/revision, exact human
   approval, governed Bridge Run, independent verification, exact-target
   integration, adopted downstream input and owner-confirmed worktree cleanup.
   The smoke may use two real Bridge owners on one physical host; it does not
   claim multiple physical machines or a live Remote Provider.
6. The rollback boundary must be exercised in a disposable target by restoring
   the verified pre-upgrade backup with matching `v0.4.2` binaries. Old binaries
   must never be started against the migrated database. Source repositories,
   unrelated worktrees and Owner credentials must remain unchanged.
7. Before and after the pre-tag gates, both inspected temporary locations must
   show no new `agentroom-*`, `agent-room-*`, `convenewire-*` or
   `convene-wire-*` directories, and the owned test-run root must be physically
   absent after cleanup.

## Protected Release Gates

After the pre-tag evidence passes:

1. Create a new annotated `v0.5.0` tag resolving to the admitted full commit
   and a new empty, non-prerelease Draft for that tag. Do not promote, retag or
   reuse the `v0.5.0-rc.3` Release or its assets.
2. Every source-consuming protected Release job must check out the one resolved
   full SHA and reconfirm that the tag still resolves to it before upload and
   verification.
3. All 19 protected Release jobs must pass, including Repository and Go gates,
   both native macOS Desktop builds, native Windows packaging and lifecycle,
   both clean-daemon Central OCI architecture executions and all archive jobs.
4. Native Windows must install current stable `v0.4.2`, upgrade in place to
   `v0.5.0`, preserve representative Owner state, verify protocol registration
   and installed/staging/ZIP executable identity, then uninstall without
   deleting Owner state.
5. Both immutable Central OCI architecture bundles must pass clean-daemon load,
   default Server readiness and build identity, and Caddy execution. Each of
   the four Central archives must consume its matching once-built bundle and
   expose a separately pinned internal checksum.
6. The closed set of exactly 22 assets must pass the tagged verifier before
   upload and after a fresh authenticated Draft download. A second clean,
   task-owned pre-publication directory must independently download and verify
   the same Draft assets.

## Publication Gates

Publication is authorized only after all pre-tag and protected gates pass:

1. Publish the Draft as non-draft and non-prerelease. It must become GitHub
   stable Latest without changing the tag or replacing any uploaded asset.
2. With GitHub credentials, netrc and user curl configuration absent, a fresh
   task-owned directory must download all 22 public assets and pass the tagged
   verifier. Public `/releases/latest` must resolve to `v0.5.0` with HTTP 200.
3. Retain the outer `SHA256SUMS` digest, total asset bytes, individual GitHub
   asset digests, publication timestamp and authenticated and anonymous
   verifier output.
4. Only after public verification, update README, release notes, website and
   version metadata from prerelease to stable. Static site, build and docs gates
   must pass, and public Pages bytes must match the exact deployed source.
5. Remove every task-owned checkout, download, database, cache, container and
   temporary root. Recheck the four historical temporary prefixes and held-
   deleted files physically rather than treating passing tests as cleanup
   evidence.

## Failure Policy

Any failed, canceled, timed-out, ambiguous or unverifiable gate authorizes no
tag movement, asset replacement, Draft publication, skipped assertion, Latest
change or completion claim. Diagnose the failure, record it, commit a bounded
repair with regression evidence, select a new exact source and rerun every gate
whose source or output may have changed.

Published and historical Release records are append-only evidence. A bad
candidate gets a new version identity; it is never repaired in place.
